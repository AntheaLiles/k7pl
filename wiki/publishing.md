# Publishing

This page is the updated publication model, replacing
`docs/WIKI-PUBLICATION.md` (deleted in the security,
decisions and docs-root closing of 2026-10-25). That
file described a superseded model in which the wiki
was generated from `docs/`; the real model since the
Lot 1 closing is the one below. **No regeneration of
the GitHub wiki has been performed in this lot, and
none may be performed without an explicit green light
from the owner, which has not been given.**

## Authority and scope

The repository is the sole authoring source. Changes
are made in `wiki/` through pull requests; the GitHub
wiki is generated output and must not be edited as an
independent source of truth.

The publication includes every file under `wiki/`.
During the refactor, the temporary migration matrix
(`wiki/_migration-matrix.md`) was excluded as a working
tool for the `docs/` → `wiki/` refactor; it was deleted
when the refactor closed on 2026-10-25 and survives in
git history. There is no
`wiki/archives/` directory to exclude.

Markdown pages are flattened into the wiki page
namespace. Their names include their source directory
path where needed, so repeated basenames remain
distinct. Non-Markdown files are copied below
`assets/`. Generated indexes provide navigation by
source directory; `_Sidebar.md` is generated as well.

## Source of truth and traceability

Each publication is tied to the exact commit SHA that
triggered it. The generated
`Publication-manifest.json` records the source path,
output path, source SHA-256, and published SHA-256
for every included file. `K7PL--Publication.md` gives
the corresponding human-readable provenance.

The SHA-256 values have a precise scope: the source
hash covers the bytes committed in `wiki/`; the
published hash covers the exact page bytes after link
rewriting and the standard provenance banner (for
`Home.md`). They do not assert that GitHub's rendered
HTML is semantically equivalent to the source
Markdown.

## CI and publication policy

The workflow is `.github/workflows/publish-wiki.yaml`.
Pull requests touching `wiki/**`, the exporter, its
tests, or the workflow itself run the exporter's
dependency-free Node.js tests and build the proposed
export without writing to the wiki. Pushes to `main`
on those paths run the same validation before
publication; `workflow_dispatch` on `main` can
republish.

The publish job runs only on a push to `main` or a
`workflow_dispatch` on `main`. It builds the
publication, clones the wiki repository, replaces its
worktree (retaining its Git history), and pushes only
fast-forward. It does not force-push or modify the
main repository. If the wiki has uncommitted or manual
pages, they are replaced by the generated export on
the next successful publication. This is intentional:
the wiki is a publication target, not a second
authoring surface.

The wiki repository must be initialized once through
GitHub before the first publication. If cloning the
wiki fails, the workflow stops with an actionable
error instead of attempting to initialize or overwrite
a repository.

The workflow uses the repository-provided
`GITHUB_TOKEN` with `contents: write` only in the
publication job. Whether GitHub permits that token to
push to the wiki must be verified by the first
controlled run; permissions or repository policy may
require a maintainer-side adjustment.

## Checks

The exporter fails on a missing `wiki/HOME.md`,
invalid UTF-8 in a Markdown page, or symbolic links
under `wiki/`. The tests cover link rewrites,
preserved resources, duplicate page basenames, the
provenance manifest, and symlink rejection. The
workflow runs the test suite on pull requests; the
repository CI retains its separate documentation-link,
REUSE, specification, Lean, and security checks.

The export is designed to be deterministic for a
fixed source tree and source SHA. It does not
guarantee resolution of every external URL, validate
Markdown rendering in GitHub itself, or replace the
repository's other checks.

## Generated status, and what is not published

The factual state page is generated by CI, not
authored, and is published by the same export once
the CI status job has generated it (the generator and
its repointing are recorded in the migration matrix).
It must not be edited by hand, and it is not linked
from here until it exists.
