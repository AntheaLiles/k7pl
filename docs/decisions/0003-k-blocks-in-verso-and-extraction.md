## Context and Problem Statement

The specification is written in Verso, used as a literate-programming tool. Exposing the real K
definition (close to EBNF) in the specification, and reusing it as is for the Lean checks,
removes the gap between what is documented and what is verified.

## Considered Options

Rejected alternatives listed by the draft:

- **Canonical `.k` files included in Verso by label**: inverts the literate logic. Kept as
  **plan B** should the Verso extension prove infeasible on the pinned version.
- **Running `kompile` at Verso elaboration**: non-reproducible, slow, environment-dependent
  build.

## Decision Outcome

Proposed decision:

1. **Normative K MUST reside only in `k` blocks** of the `SpecK.*` modules. The `.k` files are
   build artefacts generated by extraction, never versioned nor edited.
2. **Attribute contract of the blocks:**

   | Attribute | Required | Values |
   |---|---|---|
   | `module` | yes | K module name |
   | `id` | yes | stable, unique identifier; equal to the K `label` for `rule` and `automaton` |
   | `kind` | yes | `syntax`, `configuration`, `rule`, `function`, `automaton`, `orchestrator`, `bridge`, `claim`, `example` |
   | `layer` | yes (except `example`) | `1`, `2`, `3` |
   | `bridge` | if `kind=bridge` | `"i→j"` |
   | `footprint` | if `kind=automaton` | list of cells or arrays |
   | `normative` | no (default `true`) | boolean; `false` = excluded from extraction |
   | `view` | no | `k`, `ebnf`, `both` |

   The module header is declared by a `kmodule` directive (`name`, `imports`).
3. **At elaboration:** light checks only (attributes, uniqueness of `id`s, `kind`/`layer`
   consistency, content hash). Elaboration MUST NOT invoke K. Writing the specification must not
   require installing K.
4. **Deterministic extraction** (`lake exe k7pl-tangle`): grouping by module in document order,
   generated module wrappers. Produces `manifest.json` (id, module, kind, layer, footprint, hash,
   source, kfile) and `sourcemap.json`.
5. **Mandatory source map:** errors from `kompile` and from the linter MUST be mapped back to
   `Verso file:line`.
6. **Acyclic module graph:** `SpecK → tangle → KGen → Proofs → SpecDoc`. A `SpecK.*` module MUST
   NOT import `KGen` or `Proofs`.
7. **Rendering:** K highlighting, `id` anchor, EBNF view derived mechanically from the `syntax`
   productions, status badges ([ADR-0007](0007-computed-assurance-statuses.md)).
8. The exact name of Verso's code-block extension API MUST be checked on the pinned version
   ([ADR-0010](0010-pinned-versions-and-upgrades.md)). This contract is functional; it does not
   fix the API.

### Consequences

- (+) The definition displayed is exactly the one verified.
- (+) EBNF view for readers without duplicating the grammar.
- (−) No K IDE support in Lean files: compensated by the source map and a fast local loop
  (`tangle` + `kompile`).
- (−) One more tool (the extractor) in the trusted base: small, tested, deterministic.

### Confirmation

- G1: elaboration of `SpecK` (attributes, uniqueness).
- G2: identical extraction on two runs; hashes consistent with the manifest.
- G10: HTML/PDF build, valid links and anchors.

## Open questions

- **Mechanism**: PR #235 already extracts K from Verso with `tools/SpecExt/CodeArtifacts.lean`
  (`@[code_block]` expanders, a `block_extension`, extraction by `lake exe spec
  --extract-code-only` into `src/k/.build/generated/`), which differs from the contract above
  (one file per block, no attributes beyond `file`, no manifest or source map). Whether this ADR
  adopts and extends that mechanism is open (KLean instruction, §4.5).
- **Q1** — exact names and definitions of the three layers; matrix of allowed crossings. Needed
  for the `layer` and `bridge` attributes.
- Instruction conflict **X-8**: as written, `SpecDoc` imports `Proofs`, so the normative
  specification build would depend on `proofs/`, which needs K and klean output; this
  contradicts « writing the specification must not require K » unless statuses are read from
  reports at render time only.
- Instruction conflict **X-20**: the identifier format (`[a-z0-9]+(-[a-z0-9]+)*` in the plan's
  VersoK draft) differs from existing camelCase labels such as `k7AddEval`, which klean turns into
  constructor names; klean maps `-` and `.` to `_`, so `a-b`, `a.b` and `a_b` collide.
