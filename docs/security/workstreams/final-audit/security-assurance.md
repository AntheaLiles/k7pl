## 2. Ce qui résiste à l'attaque

- **Injection de script.** Toutes les expressions `${{ … }}` des blocs `run` des workflows modifiés passent par `env` ; `inputs.version` est
  validée par une regex semver **avant** l'écriture dans `$GITHUB_OUTPUT` (`release.yaml:110-117`) ; les noms de tags poussés le sont aussi ;
  `LATEST`/`CURRENT` sont revalidés dans `open-pr` (`bump-lean.yaml:139-147`) avant toute utilisation, y compris dans les `with:` de
  `create-pull-request` ; `scripts/latest-lean-version.sh` et `bump-lean.sh` filtrent `^v[0-9]+\.[0-9]+\.[0-9]+$` ; toutes les variables
  `ZENODO_*` sont validées par `load_config` avant tout réseau (`sync_zenodo.py:108-173`, URL de release sans espace et sous le bon dépôt).
  [LU]
- **Contenu d'artefacts non fiables.** `release-notes.md` n'atteint que `--notes-file` (aucune évaluation shell) ; le PDF n'est jamais
  exécuté ; l'artefact `lake-manifest` doit être un unique fichier ordinaire, non lien symbolique (`bump-lean.yaml:158-171`), et exactement trois
  fichiers suivis doivent différer, rien d'indexé ni de non suivi (`:173-184`). `for root in $roots` (`verify.yaml:138-147`) : noms issus de
  `lakefile.lean` (contenu du dépôt), sans espace par construction (`check_lean_modules.py:43`), échec propagé par `set -euo pipefail` ;
  le globbing reste théorique. [LU]
- **Astuces d'URL dans le manifeste** : majuscules dans le propriétaire ou l'hôte, `user@`, port, `..`, barre finale, doublon de paquet,
  dépendance directe marquée `inherited` : **toutes rejetées**. JSON de 5 000 chiffres et imbrication de 200 000 niveaux : rejet propre
  (`ValueError`, `RecursionError`), plafond de 1 Mio. Clé JSON dupliquée : Python garde la dernière [EXÉCUTÉ] ; Lean semble faire de même
  (`RBNode.insert`) [ESTIMÉ], donc pas de divergence d'interprétation exploitable.
- **`sync_zenodo.py`** : liens `latest_draft`/`record` restreints à `https`, au `netloc` exact de l'instance, sans requête ni fragment, suivis
  d'un identifiant entier (tests existants) ; identifiants de fichier filtrés avant d'entrer dans une URL ; somme MD5 comparée avant
  publication ; le jeton n'est jamais imprimé (assertion de la suite de tests). Pas de SSRF ni de traversée par `ZENODO_FILES_DIR` (fixé
  à `out` par le workflow ; un seul PDF exigé). [LU] ; 131 tests verts [EXÉCUTÉ].
- **Moindre privilège.** `release.yaml` : `permissions: {}` au niveau du workflow ; `check` en `contents`/`checks: read` ; vérifications en
  `contents: read` ; seul `draft` écrit, sans checkout ni code du dépôt. `zenodo.yaml` et `bump-lean.yaml` : plus aucun `contents: write` ;
  `BUMP_TOKEN` n'apparaît que dans la première étape et l'entrée `token` de `open-pr`, qui n'exécute aucun code Lean. [LU]
- **Garde « release existante »** (`release.yaml:242-251`) : liste les brouillons (jeton `contents: write`), sérialisée par `concurrency`

## 3. Ce qui n'a pas pu être vérifié, et pourquoi

- **Comportement réel de Zenodo** (redirection de `/api/records/<concept>`, forme des `links`, `newversion` quand un brouillon existe,
  latence d'indexation) : `zenodo.org` refusé par le proxy.
- **Sémantique exacte de `--signer-workflow`** et validité cryptographique d'une attestation : source de `gh` absente, hôtes Sigstore et
  d'attestation non joignables (M1 reste [ESTIMÉ]).
- **Réglages du dépôt** : environnements (API refusée par le proxy), réglage d'immuabilité, politique Actions, approbation des workflows de
  forks, méthodes de fusion autorisées, valeur réelle de `bypass_actors` : `GH_TOKEN` invalide, lecture anonyme seulement.
- **`GITHUB_SHA` d'un tag annoté** et comportement de `actions/checkout` sur un tag déplacé : non observés ; les deux cas échouent
  de façon sûre d'après la lecture, sans exécution.
- **Faisabilité actuelle de l'empoisonnement de cache** par le jeton d'exécution (M3) et **comportement de Lake** avec `subDir`, `configFile`
  ou `lakeDir` altérés (F1) : non testés (pas de toolchain Lean exécutée ici).
- **Exécution de bout en bout** de `release.yaml`, `zenodo.yaml` et `bump-lean.yaml` : jamais faite ; tout le flux reste `PREPARED`.

## 4. Verdict

L'état intégré **résiste à une revue externe sur l'hygiène des workflows** (injection, privilèges, épinglage, gardes d'échec par défaut)
et ne contient pas de régression. Il **ne résiste pas encore à une revue sévère de ses revendications** : quatre constats IMPORTANTS montrent
des contrôles présentés comme plus forts qu'ils ne sont (validation du manifeste, barrière de tags, procédure publique de vérification) et un
chemin d'échec irréversible mal géré après publication Zenodo. Aucun n'est exploitable par un contributeur externe sans droit d'écriture ;
tous sont corrigibles sans changement d'architecture. À traiter, ou à déclarer comme risques acceptés dans `THREAT-MODEL.md` et
`ASSURANCE-CASE.md`, **avant** la première release de spécification.
