# Diversity, Equity, and Inclusion Project Statement

K7PL

This DEI.md file covers the public K7PL repository and its contribution spaces, including GitHub issues, pull requests, documentation, specification, source code, tests, and project communication conducted in public project spaces.

Our project prioritizes and reflects on DEI through a regular review of project policies and performance. This reflection is documented, in part, in the following DEI.md file based on specific [CHAOSS](https://chaoss.community) DEI metrics.

### [Project Access](https://chaoss.community/?p=4953)

Project access is addressed in our project through various efforts. Through these efforts, we aim to support access for all. Specific efforts in our project include:

1. The project is developed through public GitHub issues and pull requests.
2. Contribution documentation is public, including the [contribution guide](CONTRIBUTING.md), the code of conduct, and the project's documentation and specification.
3. Contributions are not restricted to source-code changes: issues, documentation, specification work, reviews, and other substantive project contributions can be proposed through the public contribution process.
4. The project works asynchronously through GitHub so that participation does not require attendance at a fixed meeting time.

### [Communication Transparency](https://chaoss.community/?p=4957)

Communication Transparency is addressed in our project through a variety of different efforts. Through these efforts, we aim to support transparency for all. Specific efforts in our project include:

1. Project decisions and technical discussions are conducted through public issues and pull requests whenever confidentiality or security considerations do not require otherwise.
2. The current specification, implementation, tests, documentation, CI configuration, and historical project material are maintained in the public repository.
3. Security and incident information that should not be disclosed publicly is handled through the private reporting mechanisms documented in [SECURITY.md](SECURITY.md).
4. The project distinguishes current documentation from historical material so that readers can identify which statements describe the current project state.

### [Newcomer Experiences](https://chaoss.community/?p=4891)

The newcomer experience is addressed in our project through a variety of different efforts. Through these efforts, we aim to support the newcomer experience for all new members. Specific efforts in our project include:

1. A public contribution guide describes the development workflow, validation requirements, and contribution languages.
2. The repository provides a documented path from project overview to architecture, research, specification, and assurance documentation.
3. The project uses explicit contribution rules and automated CI checks so that contributors can inspect the same validation criteria before proposing a change.
4. The code of conduct and its supporting response templates provide a documented route for raising community concerns.

### [Inclusive Leadership](https://chaoss.community/?p=3522)

Inclusive leadership is addressed in our project through a variety of different efforts. Through these efforts, we aim to support leadership opportunities for project members with an interest. Specific efforts in our project include:

1. Project governance and contribution decisions are exposed through public issues and pull requests rather than relying exclusively on private communication.
2. The contribution process allows contributors to propose substantive changes and to participate in technical review before changes are merged.
3. The project is documenting its governance, assurance, and review processes so that project responsibilities and decision criteria can progressively become less dependent on undocumented maintainer knowledge.
4. The current project remains maintainer-led; formal delegation and a broader leadership structure are an identified area for future governance work.

Our project recognizes that the inclusion of the DEI.md file and the provided reflection on the specific DEI metrics does not ensure community safety nor community inclusiveness. The inclusion of the DEI.md file signals that we, as a project, are committed to centering DEI in our project and regularly reviewing and reflecting on our project DEI practices.

If you do not feel that the DEI.md file appropriately addresses concerns you have about community safety and inclusiveness, please let us know. You can do this by reporting your concerns to our [Code of Conduct](CODE_OF_CONDUCT.md) reporting process to raise concerns you have.
